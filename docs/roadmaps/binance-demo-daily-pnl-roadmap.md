# Дорожная карта: автономная торговля Binance Demo и обучение по дневному PnL

Дата: 2026-10-10. Статус: **план реализации, функции не внедрены**.
Область первого релиза: Binance Spot Demo Mode, покупки за имеющиеся средства,
без плеча и шортов. Финансовый результат здесь виртуальный. Подключение реальных
средств — отдельная фаза после проверки, а не автоматическое продолжение демо.

## 1. Новый целевой контракт

Новое назначение: автономно выбирать вход, размер позиции и выход, повышая
ожидаемый дневной финансовый результат всего счёта при фиксированном риске.
Контракт: `daily_net_equity_pnl_v1`. Пользователь подтвердил целевую метрику:
чистый дневной PnL счёта в USDT после комиссий. Поступления от продаж
публикуются отдельно. Положительный результат каждого дня не гарантируется;
бот вправе пропускать торговлю при отсутствии положительного ожидаемого эффекта.

```text
DailyTradingPnL_USDT = Equity_end - Equity_start - ExternalNetFlow
DailyReturn = DailyTradingPnL_USDT / Equity_start
EconomicPnL = DailyTradingPnL_USDT - AI_cost - allocated_infrastructure_cost
```

`Equity` включает свободные и заблокированные средства и открытые позиции.
Основное правило оценки — свежий mid одной торговой среды, переведённый в USDT
по заранее определённым маршрутам. Отдельно показывается оценка ликвидационной
стоимости по доступным bid/depth и ожидаемым расходам выхода. Нет свежей оценки
актива — нет полного дневного результата. Нельзя молча оценить его в ноль.
Изменение стоимости открытых позиций входит в PnL: удержание убыточной позиции
не скрывает убыток. Основная бизнес-метрика — средний дневной net PnL при
одинаковом начальном капитале; нормированная доходность используется для
сравнения версий. EconomicPnL дополнительно проверяет стоимость автоматизации.

Комиссии, списанные биржей, уже уменьшают equity; повторно их не вычитаем.
Исполнения по фактическим ценам уже отражают эффект исполнения; оценочный
slippage не вычитается второй раз. Отдельная атрибуция показывает комиссии,
spread/shortfall и стоимость AI. Сброс демо-баланса начинает новый эпизод;
пополнение и вывод учитываются как внешние потоки, не прибыль, с USDT-оценкой
на момент каждого перевода. Простая формула DailyReturn применяется к
сравниваемым эпизодам без внутридневных пополнений/выводов; иначе нужен
flow-adjusted time-weighted return, а день не смешивается с фиксированным бюджетом.
На период измерения счёт предназначен исключительно этому боту; ручная сделка
или неидентифицированное изменение баланса явно нарушают атрибуцию результата.

День: местные 00:00–24:00 `Europe/Budapest`, события хранятся в UTC; DST даёт
23/25-часовые дни. В отчёте: net PnL, realized PnL, изменение unrealized PnL,
equity/free/locked, комиссии, поступления продаж, оборот, максимальная просадка,
убыточные дни, прибыльные дни `n/N`, покрытие данных и версия политики.
День без новых сделок остаётся в выборке и включает переоценку overnight
позиций и других активов. Нулевой PnL возможен для неизменного полностью USDT
баланса без расходов/внешних потоков; неполный день — pending/incomplete с
причиной. После восстановления данных убытки периода сбоя входят в результат.
Для сравнения моделей неполные дни раскрываются и не превращаются в выигрыши.

Старые early capture/coverage/precision становятся диагностикой входов. Их
исторические контракты и отрицательные результаты сохраняются. Старые отчёты
не переименовываются в доказательство прибыльности нового бота. При реализации
фазы 0 новый статус регистрируется в спецификациях и индексе; активные старые
спецификации меняются только вместе с соответствующим кодом и тестами.

## 4. Подключение и исполнение

Использовать **Spot Demo Mode**. Его ключ создаётся в интерфейсе Demo Trading;
REST host — `demo-api.binance.com`, WebSocket API —
`demo-ws-api.binance.com`, market streams — `demo-stream.binance.com`.
Demo Mode и Spot Testnet — разные среды; Binance отдельно предупреждает, что
демо-результат не подтверждает реальную доходность.
[Официальное описание Demo Mode](https://github.com/binance/binance-spot-api-docs/blob/master/demo-mode/general-info.md).

Ключу нужны чтение account/history и право Spot trading. Вывод средств и
переводы не нужны. Секреты передаются через локальное защищённое хранилище,
не через сообщения, логи, ноутбуки или Git. Проектируем отдельный config с
allowlist demo hosts, capability check и запретом использования production
ключа/host. Проверяем доступность Demo Mode для конкретного аккаунта и права
в начале интеграции. Private events получаем через текущую WebSocket
подписку; используем `userDataStream.subscribe.signature` либо Ed25519
session + `userDataStream.subscribe`.
[Текущая документация подписок](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/user-data-stream).

Новые компоненты: `BinanceDemoAdapter`, `UniverseService`, `MarketDataService`,
`DecisionIntent`, `RiskManager`, единственный `OrderManager`, `AccountReconciler`,
`DailyPerformanceService`, адаптер profit evaluator/release. Начальный стек:
Python/asyncio, Decimal для денег, transactional SQLite WAL с одним владельцем
записи, журналы событий и outbox; существующий Telegram/UI — отображение.
Новый API/dashboard можно добавить без изменения источника истины — exchange
fills и сверенного ledger. JSON виртуальных позиций остаётся старым контуром.

Базовый жизненный цикл:

```text
данные → DecisionIntent → проверка риска/резерв средств → durable order intent
       → Binance send → ACK / QUERY_REQUIRED → fill ledger
       → проверенная биржевая защита → HOLD / TP / SL / signal SELL
       → подтверждённый SELL fill → reconcile → daily equity → mature dataset
```

Связи: `decision_id`, persistent `client_order_id`, exchange order/list ID,
trade ID, commission asset, position ID, policy/model version, account episode.
BUY/SELL отчёт появляется по fills, отдельно от intent/ACK/trigger.
Неизвестный результат отправки сначала проверяется по бирже; слепой повтор
заявки запрещён. Client ID сам по себе не заменяет durable журнал завершённых
решений. Биржа документирует возможность неизвестного исполнения при timeout.
[REST API и обработка статуса](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md).

TP/SL: exchange-side SELL OCO; OTOCO — вариант связанного limit-входа.
Также провести capability/integration-проверку OPOCO: выходная quantity
определяется полученными активами после полного исполнения входа. Эти варианты
не решают автоматически риск partial entry; её защита и cancel/recovery
прорабатываются отдельно. Проверять поддержку символа и фактический статус
обоих защитных ордеров, не считать PENDING_NEW активным стопом.
[Order lists](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md#order-lists),
[OPO/OPOCO и quantity](https://github.com/binance/binance-spot-api-docs/blob/master/faqs/opo.md).

Для обычного BUY с последующим OCO количество берётся из fills с учётом
доступного base balance/комиссии/округления. Если защита отклонена — блокировать
новые входы, сверить quantity/order status и выполнить заранее протестированное
восстановление защиты или аварийный выход при доступной бирже. Незащищённая
экспозиция — incident, не успешно защищённая позиция. Stop trigger не гарантирует
цену исполнения; stop-limit может остаться неисполненным. Тип защиты выбираем
по поддержке и испытаниям, а не по красивому ожидаемому PnL.

До первой покупки зарегистрировать предел незащищённой quantity/notional и
времени, исходя из проверенной задержки API и pilot budget. Они проверяются
как критерии приёмки, а не только записываются в лог. Отдельный случай — partial
BUY меньше min-notional/step защитного ордера: отменить остаток входа, сверить
fills, восстановить защиту/ограниченно закрыть доступное количество; dust
остаётся в ledger с риском и причиной. Превышение предела блокирует дальнейшие
входы и расширение canary. При недоступной бирже не обещаем моментального
закрытия и не выдаём такой цикл за успешно завершённую проверку защиты.

При сигнале SELL OMS согласует отмену защиты с её возможным fill и продаёт
только остаток. Startup/reconnect восстанавливает orders/lists/fills/balances.
Риск учитывает pending orders, резервы и locked funds всех источников сигналов.
Entry kill switch сохраняет защитные ордера; отдельный emergency-close имеет
проверяемый протокол. Нельзя удалить позицию из памяти и назвать это продажей.

## 5. Мониторинг, решения и дополнительные функции

Universe строится по demo exchangeInfo + account permissions/filters, а не
только по публичному TRADING. Храним пары и уникальные assets, права, статусы,
типы ордеров и время снимка. Cancel-only/остановленный символ нельзя покупать.
Активы с другой quote currency также наблюдаются; торговля требует доступного
quote balance и проверенной USDT-конверсии. В pilot исполнение ограничено USDT
парами; расширение явно меняет eligible trading scope, не отчёт об охвате.
Обрабатываем tick/step/min-notional/order-count и другие применимые ограничения
с Decimal и безопасным округлением.
[Фильтры Binance](https://github.com/binance/binance-spot-api-docs/blob/master/filters.md).

Лёгкий уровень данных для всех разрешённых инструментов: свечи/доходности,
объём, spread, состояние рынка, ликвидность и fresh status. Глубокие trades/L2
и order-flow признаки — для короткого списка и открытых позиций в пределах
rate budget. Для решений фиксируем event time, receive time, доступность,
закрытие свечи, gaps/update IDs и источник. Смена схем, дубли, пропуски,
листинг/делистинг и maintenance имеют явные обработчики. Demo может отдавать
устаревшие данные при обслуживании: успешный HTTP не означает свежесть.
[Demo changelog](https://github.com/binance/binance-spot-api-docs/blob/master/demo-mode/CHANGELOG.md).

Исходная политика остаётся простой и frozen для сравнения. Следующий learner
оценивает net expectancy входа и относительный приоритет кандидатов; exit head
оценивает продолжение/ослабление уже открытой позиции. Волатильность и
вероятностные оценки используются для размера/защиты, направление — для входа.
Исторические perpetual order books не объявляются Spot fill evidence.

Дополнительные функции проверяются по одной, в следующем порядке:

1. Отказ от входов с отрицательным ожидаемым результатом после издержек;
   ликвидность, spread и ограничение оборота. Эффект — меньше слабых сделок.
2. Размер позиции по stop distance/volatility и общий капитал с учётом
   коррелированных активов. Эффект проверяется при одинаковом risk budget.
3. Trailing protection, частичная фиксация, time stop и выход при истощении
   тренда. Отдельно сравнить с простым фиксированным TP/SL.
4. Ранжирование BUY и замена слабых позиций более сильными — только в полной
   портфельной симуляции, учитывающей освобождение капитала и издержки.
5. Marketable limit/ограниченная задержка исполнения по order flow — после
   сбора same-venue clocks/fills. Защитный выход не ждёт благоприятного сигнала.

Ни одна функция не объявлена повышающей PnL заранее. Leverage, мартингейл,
усреднение убытка без лимита и попытка «отбить дневную цель» в этот scope не входят.

Предложенные начальные ограничения demo canary, подлежащие проверке до запуска:
риск по стопу до 0.1% equity на сделку, notional одной позиции до 5%, общий
notional до 25%, первоначально одна открытая позиция, затем контролируемое
расширение; дневной loss stop 1%, drawdown stop 3%. Это инженерные пределы
пилота, не оптимальные параметры и не гарантия максимального убытка при gap.
Количество/сумма проверяются также против фильтров и возможного slippage.
После срабатывания: запрет новых BUY, сохранение/сопровождение защиты,
incident/reconcile и разрешённый сценарий восстановления. Learner не может
ослабить лимиты или сам увеличить выделенный капитал.

## 6. Контур обучения и финансовый release gate

Сначала supervised CatBoost/простые модели и ограниченный поиск параметров,
не бесконтрольное RL на сумме продаж. Decision dataset включает BUY/SELL/HOLD/
WAIT/BLOCK, все кандидаты и состояние капитала. Для невыбранных вариантов
доступен только будущий рыночный target; фактический account reward принадлежит
исполненной политике. Counterfactual fill/PnL помечается как симуляция.
Daily PnL служит оценкой всей политики; credit assignment к сделке не заменяет
портфельный результат. Комиссионные ставки получаем для аккаунта, фактические
расходы — из fills.
[Комиссии Spot](https://github.com/binance/binance-spot-api-docs/blob/master/faqs/commission_faq.md).

Ежедневный ingestion и readiness; обучение по расписанию только при достаточном
приросте созревших данных. Политика между разрешёнными обновлениями стабильна.
Обучение на полной истории закрывшихся сделок не считается «онлайн», если
feature/label clocks не подтверждены. Legacy virtual fills не становятся demo
labels. Данные после даты fit не участвуют ни в scaler, ни в calibration,
подборе параметров или threshold.

Каждая гипотеза регистрирует до результатов: вопрос, primary metric,
популяцию, период, risk budget, practically meaningful эффект, параметры,
baseline, число сравнений, cost/compute budget, правила verdict и rollback.
Walk-forward по времени, train-only transforms, purge/embargo по target/holding
overlap; одинаковые universe snapshots и стартовый капитал. Replay полностью
воспроизводит cash, BUY/HOLD/SELL, partial fills/exits, TP/SL, capacity,
replacement и cooldown обеих политик. Если в свече одновременно достижимы TP
и SL — finer data или заранее выбранное неблагоприятное исполнение.

Использовать **maximum available historical period**, включая рост/падение,
листинги/делистинги и реальные candidate states. Проверить PIT universe и
receipt provenance; отсутствие исторической сертификации раскрыть, не
подменять текущим списком победителей. Доступная максимальная история —
обязательный этап, но уже просмотренные даты не являются новым sealed test.
До изменения поведения требуется отдельный ранее не просмотренный forward.
Временное техническое demo испытание текущей политики не выдаёт financial PASS.

Три контроля: frozen текущая политика, USDT/no-trade, BTC buy-and-hold с тем же
начальным капиталом и явным риском. BTC — диагностика рыночного режима/alpha,
а обязательные финансовые проверки — способность зарабатывать относительно
USDT и улучшение относительно champion при фиксированном риске.
Убыточный кандидат, который теряет меньше champion, ещё не доказал заработок.

До запуска выбрать одну primary гипотезу и фиксированный срок/объём оценки,
минимальный эффект, уровень 95% и block length по training данным. Для группы
сравнений применять заранее выбранную Holm-коррекцию; bootstrap сам не исправляет
множественные проверки. Ежедневные отчёты не разрешают завершить тест при первом
появлении значимости. Промежуточный statistical stop требует отдельного
зарегистрированного последовательного протокола. Risk stop действует всегда,
его срабатывание сохраняется как результат попытки, не стирает убытки.

Forward сравнительный отчёт разделяет одинаково симулированные портфели и
фактические исполнения. Для actual-fill uplift candidate/champion нужны
изолированные, сопоставимые demo budgets: отдельные доступные demo accounts
либо отдельно учитываемые, реально торгуемые OMS subportfolios с `arm_id`,
без перекрёстного финансирования и с проверяемой суммой ledger к общему счёту.
Вариант проверяется по возможностям аккаунта в фазе 0/1; одинаковые API keys
одного аккаунта не создают независимые бюджеты. Общий риск обоих arms ограничен.
Каждый intent/order/fill/fee и резерв имеет неизменный `arm_id`, отдельные
ордера без межполитического неттинга. Одинаковы стартовый бюджет, лимиты и
доступные данные; реакция на общий risk stop симметрична и задана заранее.
Перераспределение исполнения после получения результата запрещено. Вывод
относится к проверенному размеру arm; масштабирование капитала проверяется
отдельно и не следует автоматически из успеха небольшого бюджета.
Если такое сравнение не обеспечено, paired forward shadow остаётся симуляцией,
фактический demo PnL публикуется отдельно; actual-fill превосходство не заявляется.

**READY_FOR_CANARY** требует технической готовности, maximum-history и нового
sealed/forward исследования внутри зарегистрированных ограничений. Оно
разрешает ограниченный демо-эксперимент, а не доказанный прибыльный релиз.
**PROMOTED** требует отдельного нового canary cohort с заранее определённым
финансовым протоколом ниже. Одна выборка не используется повторно для обоих
решений. При отсутствии требуемого типа фактического evidence остаётся
ограниченный исследовательский статус, а не автономная promotion.

Для автономной финансовой demo promotion одновременно нужны:

- Независимо сверенные деньги, fills, valuations, часы и покрытие, согласованные
  версии source/data/model/objective и полный журнал всех попыток.
- Положительный net PnL и положительная нижняя граница заранее выбранного
  интервала средней дневной доходности против USDT/no-trade; paired delta
  candidate–champion с нижней границей выше 0 и достаточным практически важным
  эффектом. Calendar-block/bootstrap учитывает зависимость дней;
  неодинаковые траектории получают собственные портфели.
- Первоначально минимум 30 полных новых дней и 100 закрытых сделок как нижний
  порог, плюс достаточная мощность проверки; сами эти количества не дают PASS.
  При низком обороте длительность увеличивается, сделки ради квоты запрещены.
- Лимиты drawdown/day loss/exposure/связанных активов соблюдены; результат не
  держится на одной монете/аномальном дне; cost/latency/gap stress не разрушает
  вывод. Нет критических OMS/защитных инцидентов без устранения.
- TH-01..12, актуальный full PASS, независимый audit, отдельный bounded canary,
  проверенный rollback и сравнение последующего fresh cohort.

Хранить SUPPORTED / REJECTED / INCONCLUSIVE с причиной; недостаток данных
запускает план сбора/увеличения выборки, а не принудительный победный verdict.
Никакая система проверки не обещает, что положительная стратегия существует.

Автоматический governor может менять только заранее зарегистрированные
параметры: entry thresholds, ranker/exit model version, TP/SL/trailing параметры
в проверенном пространстве. Не может менять цель, среду, риск, equity budget
или себе выдавать права. Новая модель не передаёт новые действия прямо в OMS:
immutable artifact → evaluation → release ticket → canary pointer → rollback.
LLM при необходимости предлагает типизированные гипотезы; deterministic
evaluator считает деньги, а governor разрешает релиз. Дополнительная ценность
LLM проверяется против простого поиска с учётом стоимости и задержки.

## 7. Проверки и эксплуатация

Тесты при реализации соответствующих фаз:

| Группа | Обязательные случаи |
|---|---|
| Денежный контракт | Покупка за 100/продажа за 90 даёт убыток, хотя proceeds=90; overnight переоценка без новых сделок; BNB/base/quote fee; отсутствие двойного вычета; reset/flows и return denominator; DST; missing valuation; known loss после сбоя. |
| Adapter/OMS | Подпись и permissions; filters/Decimal; duplicate intent/event; timeout после успешного send; partial fill/cancel, защитный min-notional и dust; пределы незащищённого notional/time; SELL против TP/SL fill; отказ защиты; restart/reconnect; locked funds; несколько signal producers. |
| Data | Недоступные/новые/остановленные символы; all-universe denominators; stale/candle not closed; gaps/out-of-order; receipt cutoff; schema change; same-venue source identity. |
| Research | Future-prefix invariance; mature-only fit; train-only transforms; purge; собственный cash ledger каждой политики; actual vs simulated arms; intrabar ambiguity; partial exits; fixed horizon/коррекция сравнений; неизменённый baseline; историческое покрытие и независимый пересчёт. |
| Release | Подделанный/stale ticket; превышение scope/risk budget; незавершённый тест; READY_FOR_CANARY vs PROMOTED и новый cohort; rejected experiment; нет power; reset episode; rollback/open orders; entry kill switch сохраняет exits. |

В эксплуатации: uptime/data lag, account reconciliation difference,
unprotected quantity/time, order latency/rejects/query-required, резерв средств,
exposure, equity/PnL/DD, комиссия и turnover, calibration/drift/label lag,
размер/полнота обучающей выборки. Дневной отчёт показывает финансовый результат
и решения с reason/model version; отчёт обучения — baseline/candidate,
периоды/n/N, CI, cost, coverage, ограничения и факт последнего разрешённого
обновления. Рост числа экспериментов не является ростом заработка.

Backup/restore ledger и cursor, один владелец аккаунта/OMS, supervisor,
reconnect с reconcile, rate budget и incident журнал обязательны до 24/7.
Каждый code/behavior change: зарегистрированная спецификация, focused tests,
relevant tests + `git diff --check`, review/stage intended source/spec/test,
`truth_harness.py change --staged`, commit и push. Runtime/keys/logs/weights
не коммитятся. Этот документ фиксирует план, не включает demo execution и
не меняет текущие BUY/SELL или обучение.
